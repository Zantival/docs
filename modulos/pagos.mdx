FusaShop procesa los pagos a través de **Wompi** (Bancolombia), una de las pasarelas de pagos más utilizadas en Colombia. El flujo combina una redirección al Web Checkout de Wompi (lado del cliente) con una confirmación server-to-server vía webhook firmado con SHA-256 para garantizar la integridad del pago aunque el usuario cierre el navegador antes de volver. Toda la lógica está implementada en `PaymentController` y en el servicio `WompiService`.

## Flujo de checkout

El proceso de pago comienza cuando el consumidor confirma su carrito en `POST /shop/checkout`.

<Steps>
  <Step title="El consumidor confirma el pedido">
    El método `checkoutProcess` del `ConsumerController` valida la dirección de envío y el método de pago (`card`, `transfer` o `cash`). Se crea la orden con `status = 'pending'` y `payment_status = 'pending'` (el estado final se confirma vía webhook).
  </Step>
  <Step title="Generación de parámetros Wompi">
    `WompiService::getCheckoutParams($order)` construye el array de parámetros requeridos por Wompi, incluyendo la referencia única `ORDER-{id}-{timestamp}`, el monto en centavos y la firma de integridad SHA-256.
  </Step>
  <Step title="Redirección al Web Checkout de Wompi">
    El navegador del consumidor es enviado al checkout de Wompi (sandbox o producción según la variable `WOMPI_ENV`).
  </Step>
  <Step title="Wompi procesa el pago">
    El consumidor ingresa sus datos de pago directamente en la plataforma de Wompi (tarjeta, PSE, Nequi, Bancolombia), sin que FusaShop maneje información sensible.
  </Step>
  <Step title="Redirección de respuesta (frontend)">
    Wompi redirige al consumidor a `GET /payment/response` con el parámetro `id` de la transacción.
  </Step>
  <Step title="Confirmación webhook (backend)">
    En paralelo, Wompi envía `POST /payment/webhook` al servidor con el evento firmado. Este es el paso que actualiza la base de datos.
  </Step>
</Steps>

## Firma de integridad

`WompiService` genera la firma SHA-256 requerida por Wompi para validar la integridad de la solicitud:

```php title="WompiService.php — generateSignature()"
public function generateSignature($reference, $amountInCents, $currency)
{
    // Formato: reference + amountInCents + currency + integritySecret
    $concatenated = "{$reference}{$amountInCents}{$currency}{$this->integritySecret}";
    return hash('sha256', $concatenated);
}
```

La referencia de la orden sigue el formato `ORDER-{id}-{timestamp}`, por ejemplo `ORDER-142-1717000000`. Este formato es crucial para que el webhook pueda recuperar el ID de la orden:

```php title="PaymentController.php — webhook() — extracción del ID"
// Extraer ID de pedido de la referencia (ORDER-ID-TIME)
$parts = explode('-', (string) $reference);
if (isset($parts[1])) {
    $orderId = $parts[1];
    $order = Order::find($orderId);
    // ...
}
```

## Endpoint de respuesta (frontend)

**`GET /payment/response`** — Wompi redirige al consumidor aquí al terminar la transacción con el parámetro `id` de la transacción.

<CodeGroup>
```php title="PaymentController.php — response()"
public function response(Request $request)
{
    $transactionId = $request->get('id');

    $status  = 'pending';
    $message = 'Tu pago está siendo procesado.';
    $reference = null;

    if ($transactionId) {
        $tx = $this->wompi->getTransaction($transactionId);
        $reference = $tx['reference'] ?? null;

        if (($tx['status'] ?? null) === 'APPROVED') {
            $status  = 'success';
            $message = '¡Pago aprobado con éxito! Gracias por tu compra.';
        } elseif (($tx['status'] ?? null) === 'DECLINED') {
            $status  = 'error';
            $message = 'El pago fue rechazado. Intenta con otro medio.';
        }
    }

    return view('payment.result', compact('status', 'message', 'reference'));
}
```
</CodeGroup>

<Info>
  Este endpoint **solo muestra un mensaje al usuario**. No actualiza la base de datos. La actualización real se realiza en el webhook para garantizar consistencia incluso si el usuario cierra el navegador.
</Info>

### Estados de la transacción Wompi

| Estado | Significado | Estado mostrado |
| --- | --- | --- |
| `APPROVED` | Aprobado | `success` |
| `DECLINED` | Rechazado | `error` |
| `VOIDED` | Anulado | `error` |
| `PENDING` | Pendiente | `pending` |
| `ERROR` | Error interno | `pending` |

## Endpoint de webhook (backend)

**`POST /payment/webhook`** — Wompi lo llama directamente desde sus servidores (server-to-server) enviando el evento `transaction.updated` con una firma `checksum`.

<CodeGroup>
```php title="PaymentController.php — webhook()"
public function webhook(Request $request)
{
    Log::info('Wompi Webhook received', $request->all());

    $payload    = $request->all();
    $signature  = $payload['signature']['checksum'] ?? null;
    $properties = $payload['signature']['properties'] ?? [];
    $timestamp  = $payload['timestamp'] ?? null;

    // Validar firma: sha256(concat(props) + timestamp + eventsSecret)
    $concatenated = '';
    foreach ($properties as $prop) {
        $concatenated .= data_get($payload['data'], $prop);
    }
    $concatenated .= $timestamp . config('services.wompi.events_secret');
    $expected = hash('sha256', $concatenated);

    if (!hash_equals($expected, (string) $signature)) {
        return response('Invalid signature', 401);
    }

    $tx        = $payload['data']['transaction'] ?? [];
    $reference = $tx['reference'] ?? null;
    $status    = $tx['status'] ?? null;

    $parts = explode('-', (string) $reference);
    if (isset($parts[1])) {
        $orderId = $parts[1];
        $order   = Order::find($orderId);

        if ($order) {
            if ($status === 'APPROVED') {
                $order->update(['payment_status' => 'paid', 'status' => 'processing']);

                // Enviar recibo al consumidor
                try {
                    Mail::to($order->user->email)
                        ->send(new OrderReceipt($order->load('items.product', 'user')));
                } catch (\Exception $e) {
                    Log::error('Error sending receipt email: ' . $e->getMessage());
                }
            } elseif (in_array($status, ['DECLINED', 'VOIDED', 'ERROR'], true)) {
                $order->update(['payment_status' => 'failed']);
            }
        }
    }

    return response('OK', 200);
}
```
</CodeGroup>

<Warning>
  El webhook debe responder con HTTP `200 OK` para que Wompi no reintente la notificación. Si la firma es inválida responde `401` y Wompi reintenta el envío varias veces siguiendo su política de reintentos.
</Warning>

### Lógica de estados en el webhook

| `status` de Wompi | Acción sobre la orden |
| --- | --- |
| `APPROVED` | `payment_status → paid`, `status → processing`, envía `OrderReceipt` por email |
| `DECLINED` | `payment_status → failed` |
| `VOIDED` | `payment_status → failed` |
| `ERROR` | `payment_status → failed` |
| `PENDING` | Se ignora, se espera el siguiente evento |

## Máquina de estados de la orden

El modelo `Order` define dos campos de estado independientes: `status` (estado logístico) y `payment_status` (estado de pago).

### Estado logístico (`status`)

```text
pending → processing → shipped → delivered
                                       ↑
                  cancelled ←──────────┘ (desde cualquier estado previo a delivered)
```

<Accordion title="Descripción de cada estado logístico">

| Estado | Descripción |
|--------|-------------|
| `pending` | La orden acaba de crearse, esperando confirmación de pago |
| `processing` | Pago confirmado, el comerciante está preparando el envío |
| `shipped` | El pedido fue entregado al servicio de mensajería (guía Envia.com generada) |
| `delivered` | El consumidor recibió el pedido |
| `cancelled` | La orden fue cancelada antes de entregarse |

</Accordion>

### Estado de pago (`payment_status`)

```text
pending → paid
       → failed
```

| Estado | Descripción |
|--------|-------------|
| `pending` | Pago iniciado, aún sin confirmar (estado inicial) |
| `paid` | Wompi confirmó el pago exitosamente (`status = APPROVED`) |
| `failed` | Pago rechazado, anulado o con error (`DECLINED`, `VOIDED`, `ERROR`) |

<Note>
  Los estados `status` y `payment_status` se gestionan por separado. Una orden puede tener `payment_status = paid` y `status = processing` simultáneamente. El comerciante es responsable de avanzar el `status` logístico desde su panel, generalmente a partir de la generación de la guía en [Envia.com](/integraciones/envia).
</Note>

## Configuración del servicio Wompi

`WompiService` lee su configuración desde `config/services.php` (que a su vez toma valores de `.env`):

<CodeGroup>
```php title="WompiService.php — __construct()"
$this->publicKey       = config('services.wompi.public_key');
$this->privateKey      = config('services.wompi.private_key');
$this->integritySecret = config('services.wompi.integrity_secret');
$this->eventsSecret    = config('services.wompi.events_secret');
$this->env             = config('services.wompi.env', 'sandbox');

$this->checkoutUrl = $this->env === 'production'
    ? 'https://checkout.wompi.co/p/'
    : 'https://checkout.co.uat.wompi.dev/p/';

$this->apiUrl = $this->env === 'production'
    ? 'https://production.wompi.co/v1'
    : 'https://api-sandbox.co.uat.wompi.dev/v1';
```

```env title=".env — variables de Wompi"
WOMPI_PUBLIC_KEY=pub_test_xxxxxxxxxxxxxxxxxxxxxxxx
WOMPI_PRIVATE_KEY=prv_test_xxxxxxxxxxxxxxxxxxxxxxx
WOMPI_INTEGRITY_SECRET=test_integrity_xxxxxxxxxxxxxxxx
WOMPI_EVENTS_SECRET=test_events_xxxxxxxxxxxxxxxxxxxx
WOMPI_ENV=sandbox
```
</CodeGroup>

<Tip>
  Para pruebas en desarrollo, usa `WOMPI_ENV=sandbox` y las llaves `pub_test_`/`prv_test_`. Wompi ofrece tarjetas y cuentas de prueba disponibles en su documentación oficial. Cambia a `WOMPI_ENV=production` con las llaves `pub_prod_`/`prv_prod_` solo en producción.
</Tip>

## Correo de recibo (`OrderReceipt`)

Cuando el webhook confirma un pago exitoso (`APPROVED`), FusaShop envía automáticamente un correo al consumidor usando la clase mailable `App\Mail\OrderReceipt`. El correo incluye el detalle de los ítems y el total del pedido, cargados con `$order->load('items.product', 'user')`.

Los errores en el envío del correo se registran en el log pero **no interrumpen** el proceso de actualización de la orden, garantizando la consistencia del estado en base de datos.
